Why did our LiteLLM usage jump, and are the spend logs complete?

Compare two periods of LiteLLM spend logs to see which models and keys drove a change, and which records have incomplete usage.

Run it on your data

Connect to your existing LiteLLM Postgres database with approved read-only access. fleetdiff takes a private snapshot, investigates it locally and removes the temporary export. No psql or model API key is needed. Already have a request-level CSV, JSON or JSONL file? Use the manual export and file path below; the Usage dashboard's daily aggregate is a different format.

1. Install fleetdiff v0.12.0

Requires curl, gh, shasum and tar on Linux or macOS (amd64 or arm64). GitHub CLI need not be signed in. This pinned installer verifies the release archive, checksums and build attestations before extraction. Start without an existing bin folder; see manual release verification for the checks.

curl -fsSLo install-fleetdiff.sh https://raw.githubusercontent.com/llm-measurement/fleetdiff/6089061c931fa19fac876e40b3809fdea4792ab8/scripts/install.sh
sh install-fleetdiff.sh v0.12.0 ./bin

2. Investigate your database

Have your administrator provision the reviewed read-only role and column grants. Role creation is an administrator action, never a write by fleetdiff. Set DATABASE_URL_FILE to the path of an approved credential file using the requirements below, leaving FLEETDIFF_LITELLM_DATABASE_URL unset.

./bin/fleetdiff investigate --litellm-db \
  --database-url-file "${DATABASE_URL_FILE:?set the approved credential file path}" --group-by key

The default compares the last 14 complete UTC days as two adjacent seven-day periods, ending at today's UTC midnight. It is clock-based; sparse logs do not establish complete coverage. For other windows, supply both --before-period and --after-period as equal-duration, ordered, nonoverlapping UTC dates or RFC3339 intervals. Add --daily to check daily row coverage, or --routing-audit for the model mix behind each route.

Credentials and private exports

The URL file must be a regular file owned by your effective user, mode exactly 0600, with no symlink path components. Have your approved secret-delivery process place it in a private directory outside your checkout. DATABASE_URL_FILE contains only that path. Never put a password or literal database URL in command arguments, shell history, scripts or reports.

Alternatively, have your secret mechanism supply FLEETDIFF_LITELLM_DATABASE_URL and omit the file option. Use exactly one credential source:

./bin/fleetdiff investigate --litellm-db --group-by key

Remote connections require sslmode=verify-full to verify both the certificate chain and hostname; sslrootcert may select a local CA file. Only numeric loopback or Unix sockets may use explicit sslmode=disable. Native mode ignores inherited PG* settings and does not load pgpass, PostgreSQL services or client certificates. The only URL query keys are sslmode, optional sslrootcert and host for an absolute Unix socket directory. Use the manual psql path for service or client-certificate setups, not a TLS override.

Only explicit database modes connect to your chosen Postgres server; file-based analysis stays offline. Reads use one read-only repeatable snapshot and exclude prompts, responses and whole metadata objects. Temporary exports are removed after analysis. --keep-export NEWDIR retains a completed private export: a mode-0700 directory and mode-0600 files, published atomically without replacing an existing path. Raw identities remain private in exports; reports use aliases. The export limits and failure rules explain timeouts, bounds and staging cleanup.

Manual psql alternative or an existing export

Requires psql and approved read-only access configured as the PostgreSQL service litellm_readonly. Replace the example UTC RFC3339 bounds below with 16 days of your data; the end is exclusive. File-based investigation excludes potentially partial first and last days before choosing its two complete seven-day periods. This differs from the native database mode's clock-based 14-day window. The projection targets LiteLLM v1.104.0. Start without an existing litellm-export folder.

set -eu
umask 077
START_UTC=2026-09-23T00:00:00Z
END_UTC=2026-10-09T00:00:00Z
curl -fsSLo export.sql https://raw.githubusercontent.com/llm-measurement/fleetdiff/v0.12.0/examples/litellm-spend/export.sql
mkdir ./litellm-export
psql 'service=litellm_readonly' -Xq -v ON_ERROR_STOP=1 \
  -v start_utc="${START_UTC:?set the export start in UTC}" \
  -v end_utc="${END_UTC:?set the export end in UTC}" \
  -v csv_file='./litellm-export/spend.csv' -f export.sql \
  >./litellm-export/private-psql.out 2>./litellm-export/private-psql.err
printf 'Exported request-level rows to ./litellm-export/spend.csv\n'

The transaction is read-only and excludes prompts, responses and whole metadata objects. It includes identities needed for local grouping, so keep the export and database diagnostics private.

Using the installed binary, analyze the export above or replace its path with your existing request-level file:

./bin/fleetdiff investigate --litellm-spend ./litellm-export/spend.csv --group-by key

The default compares two complete seven-day periods. For sparse or shorter exports, select explicit --before-period and --after-period dates. Choose --group-by team, user, end-user or session for another view.

The export, install and investigate path and spend export guide cover fields and period choices. For continuous metrics and summary windows, use the collector's LiteLLM recipe.

What you'll see

Example output from the synthetic sample below; your values will reflect your input.

Recorded tokens doubled (8,000 -> 16,000).
model-1 accounts for 100% of the net recorded increase (+8,000 tokens).
Logged model requests: 8 -> 12.

Recorded tokens doubled, while logged model requests grew from eight to twelve. fleetdiff separates model-by-model usage changes from contributor rankings and completeness.

Who drove the increase?
  key-1: 5,000 -> 10,000 tokens; change +5,000.
  key-2: 1,000 -> 4,000 tokens; change +3,000.
  key-3: 2,000 -> 2,000 tokens; change +0.
  2 leading tracked keys account for 100% of the net recorded increase.
  Attributed tokens: 8,000 -> 16,000.

Two keys account for the increase. The contributor section uses local aliases for the keys.

How complete is the export?
  Records needing usage review (categories may overlap): 2 -> 4.
  Zero-only records, origin unknown: 2 -> 4.
  Failed records (overlap usage categories): 1 -> 2.

The completeness section points to zero-only and failed records worth checking in LiteLLM. To check usage and identity fields in your telemetry, see Do my LLM traces record token usage and user IDs?

To compare the number of exported rows with LiteLLM's daily request counts, see Are all our requests actually in the spend log?. To see the model mix behind an original route, use the routing audit. To re-price the recorded usage under another model mix, see What would switching models have cost?

No data handy? Try the sample

Requires curl, gh, shasum and tar. Linux or macOS, amd64 or arm64. The sample uses the released binary and a synthetic CSV.

curl -fsSLo fleetdiff-source.tar.gz https://github.com/llm-measurement/fleetdiff/archive/refs/tags/v0.12.0.tar.gz
tar -xzf fleetdiff-source.tar.gz
cd fleetdiff-0.12.0
sh scripts/install.sh v0.12.0 ./release
./release/fleetdiff investigate --litellm-spend examples/litellm-spend/synthetic.csv \
  --before-period 2026-10-07 --after-period 2026-10-08

Source and reproduction: released synthetic CSV and accounting and privacy checks. Verification record.

This synthetic example compares logged model requests; zero-only records retain unknown origin, and failed records can overlap usage categories.
