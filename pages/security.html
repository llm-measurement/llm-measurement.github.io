Review what each tool reads, where it runs, and how to verify the exact release before using your data.

Data paths

  • fleetdiff v0.12.1 runs on your machine. File-based analysis of spend exports, summaries, collector configurations and OTLP captures (including stdin) stays offline, even when database credentials are present in the environment. Only explicit --litellm-db or export litellm modes connect to the chosen Postgres server, with DNS resolution if needed; they make no telemetry, update or provider requests. Installation separately downloads release files. See the network-boundary guard and network-isolated file-command CI checks.
  • The collector runs inside your pipeline. Its configured exporters send metrics and original spans to your selected destinations; optional summary files stay on the configured volume.
  • llm-sketchkit runs inside your Go or Python process. Your application chooses the identities to hash and where to store or share the summaries.

The read-only LiteLLM SQL projection selects request metadata and usage fields, excluding prompts and responses. The request-level export still contains raw identity columns; keep it private and give the export role SELECT access only. The export recipe writes to a restricted local directory.

LiteLLM database access

Native export uses one read-only repeatable snapshot and excludes prompts, responses and whole metadata objects. The reviewed column grants include access to the source metadata column, but the fixed export projection does not export the whole object. Role creation and authentication setup are administrator actions, never writes by fleetdiff.

Credentials

When using --database-url-file, leave FLEETDIFF_LITELLM_DATABASE_URL unset. GitHub CLI must be installed for the release installer but need not be signed in. Start without an existing bin folder; the installer refuses to replace it.

Use exactly one credential source: an approved environment secret or a URL file. The file must be a regular file owned by your effective user, mode exactly 0600, with no symlink path components. Have your approved secret-delivery process place it in a private directory outside your checkout. Never put a password or literal database URL in command arguments, shell history, scripts or reports.

The database guide uses a file. Alternatively, after installing fleetdiff there, have your secret mechanism supply FLEETDIFF_LITELLM_DATABASE_URL and omit the file option:

./bin/fleetdiff investigate --litellm-db --group-by key

Transport and configuration

Remote connections require sslmode=verify-full to verify both the certificate chain and hostname; there is no plaintext fallback. sslrootcert may select a local CA file. Only numeric loopback or Unix sockets may use explicit sslmode=disable. Native mode ignores inherited PG* settings and does not load pgpass, PostgreSQL services or client certificates. The only URL query keys are sslmode, optional sslrootcert and host for an absolute Unix socket directory. Use the manual psql path for service or client-certificate setups, not a TLS override.

Periods and retained exports

Native investigation defaults to two adjacent seven-day periods ending at today's UTC midnight. The selection is clock-based; sparse logs do not establish complete coverage. For other windows, supply both --before-period and --after-period as equal-duration, ordered, nonoverlapping UTC dates or RFC3339 intervals. File-based investigation instead excludes potentially partial first and last days before selecting two complete seven-day periods.

Temporary exports are removed after analysis. --keep-export NEWDIR retains a completed private export: a mode-0700 directory and mode-0600 files, published atomically without replacing an existing path. Exports and database diagnostics contain private information; raw identities remain in exports, while reports use aliases.

A manual spend export needs 16 days of input for the file-default comparison. Set RFC3339 UTC bounds, with an exclusive end; daily coverage requires both bounds at UTC midnight. Keep the same scope, filters and retention for paired exports, and let asynchronous writers settle. File commands may select explicit comparison periods for shorter exports. Native investigation defaults to the last 14 complete UTC days; session review and what-if can select a single period. Their released guides describe the interval rules.

The psql recipes need a PostgreSQL service named litellm_readonly, read-only access, and new export directories. The routing export adds routing_details=true. These projections target LiteLLM v1.104.0 and export request-level rows; a Usage dashboard aggregate is not a substitute. Keep the paired helper files together and keep exports, private-psql.out and private-psql.err private. A private snapshot aligns the reads, not the completion of separate writers.

Recorded data and attribution

Failure-row usage has unknown finality. Recorded fallback counters do not reconstruct physical attempts. A zero denominator gives an unknown share. The routing audit does not establish causal savings or quality equivalence.

Zero-only usage has unknown origin; failed records can overlap other review categories. A failure row's gateway-recorded tokens have unknown finality. Routing reports show the gateway-selected model with a deployment ID, rather than independent provider confirmation. Exact public model names from the price catalog are readable; private model and deployment names stay aliased even with --show-labels. That flag reveals only recorded route and agent labels. Fallback counters do not reconstruct physical attempts; missing original routes are not inferred from a recovery route. Only pass_through_endpoint rows marked autorouter_classifier count as classifier overhead.

Daily counts are LiteLLM's second accounting path, rather than an independent request count. The pinned runtime omits failures from both tables when failure logging is off; successful response-cache hits count in both without a provider call. These are logged spend-transaction counts, not all incoming requests or physical sends. An absent daily row is unknown, partial UTC days have no inferred missing count, and extra exported rows are a discrepancy to review. Matching counts cannot reveal shared omissions.

See the credential and publication contract, export limits and failure rules for timeouts, bounds and staging cleanup, real-PostgreSQL export checks and TLS transport tests.

Identity handling

Canonicalized identities are keyed with HMAC-SHA256 before entering sketches. Supported user, session and prompt values appear as keyed hashes in summaries and as aliases in fleetdiff's default reports, rather than raw IDs. These identifiers are pseudonymous: protect the key and access to linkable outputs. Use compatible identity fields, domains and keys when combining summaries. See the hashing contract and report-sharing guidance.

The collector's original trace stream and local captures retain their source data. Configure content capture and backend access separately; hashing the selected ranking fields does not redact the original spans. Summary metadata such as producer and scope names is cleartext.

Verify fleetdiff without piping a script to a shell

Use trusted installations of curl, GitHub CLI (gh), shasum and tar. These commands download files into a new directory, verify build provenance for the archive, checksum manifest and SPDX SBOM, check the archive's checksum, then extract. Choose your platform using the two variables below. The release has Linux and macOS archives for amd64 and arm64.

set -eu
umask 077
review=$(mktemp -d ./fleetdiff-review.XXXXXX)
cd "$review"
os=$(uname -s | tr '[:upper:]' '[:lower:]')
case $(uname -m) in arm64|aarch64) arch=arm64 ;; x86_64|amd64) arch=amd64 ;; *) exit 1 ;; esac
case "$os" in linux|darwin) ;; *) exit 1 ;; esac
archive="fleetdiff_v0.12.1_${os}_${arch}.tar.gz"
base=https://github.com/llm-measurement/fleetdiff/releases/download/v0.12.1
for file in "$archive" SHA256SUMS provenance.jsonl sbom.spdx.json; do
  curl --proto '=https' --tlsv1.2 -fL "$base/$file" -o "$file"
done
for file in "$archive" SHA256SUMS sbom.spdx.json; do
  gh attestation verify "$file" --bundle provenance.jsonl \
    --repo llm-measurement/fleetdiff \
    --signer-workflow llm-measurement/fleetdiff/.github/workflows/release.yml \
    --source-ref refs/tags/v0.12.1 --deny-self-hosted-runners
done
shasum -a 256 --ignore-missing -c SHA256SUMS
mkdir verified
tar -xzf "$archive" -C verified
./verified/fleetdiff --version

Release assets include SHA256SUMS, public Sigstore build provenance and an SPDX SBOM. The pinned release workflow records how they are produced. Provenance binds artifact bytes to a workflow and source ref; review the source and dependencies for your own deployment.

Verify the collector image and Helm chart

Use trusted curl, gh, shasum and Cosign tooling, with GitHub CLI signed in for the OCI provenance API checks. Downloads and Cosign registry checks use public artifacts. The v0.6.1 image and chart 0.6.1 share the collector release workflow and tag. Verify the release metadata and immutable OCI digests before pulling or deploying; these commands perform signature and build-provenance checks without starting a container or changing a cluster.

set -eu
umask 077
review=$(mktemp -d ./collector-review.XXXXXX)
cd "$review"
release=v0.6.1
base=https://github.com/llm-measurement/otelcol-genai-sketches/releases/download/$release
for file in image-digest.txt chart-digest.txt SHA256SUMS provenance.jsonl sbom-index.json; do
  curl --proto '=https' --tlsv1.2 -fL "$base/$file" -o "$file"
done
for subject in SHA256SUMS sbom-index.json; do
  gh attestation verify "$subject" --bundle provenance.jsonl \
    --repo llm-measurement/otelcol-genai-sketches \
    --signer-workflow llm-measurement/otelcol-genai-sketches/.github/workflows/release.yml \
    --source-ref "refs/tags/$release" --deny-self-hosted-runners
done
shasum -a 256 --ignore-missing -c SHA256SUMS
identity=https://github.com/llm-measurement/otelcol-genai-sketches/.github/workflows/release.yml@refs/tags/$release
image="$(cat image-digest.txt)"
chart="$(cat chart-digest.txt)"
for artifact in "$image" "$chart"; do
  cosign verify --certificate-identity "$identity" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com "$artifact"
  cosign verify-attestation --type slsaprovenance1 \
    --certificate-identity "$identity" \
    --certificate-oidc-issuer https://token.actions.githubusercontent.com "$artifact"
  gh attestation verify "oci://$artifact" \
    --repo llm-measurement/otelcol-genai-sketches \
    --cert-identity "$identity" --source-ref "refs/tags/$release" \
    --deny-self-hosted-runners
done

The collector release publishes image and chart digests, SHA256SUMS and an SPDX SBOM index for both image platforms. The signed image index binds the platform SBOM content through OCI digests; the downloaded checksum file alone is an integrity check, not the authentication step. See Deployment for anonymous pulls, provenance verification and Helm installation, and the release workflow for the build.
