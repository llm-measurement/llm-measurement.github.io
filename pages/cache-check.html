Compare recorded cache reuse before and after a change, and find which keys or sessions added uncached input.

Run it on your data

A request-level LiteLLM export such as spend.csv, or read-only access to the proxy’s Postgres database to create one. Use the read-only export recipe; the Usage dashboard’s daily aggregate is a different format. Include the default cache columns from the projection tested on LiteLLM v1.104.0; missing detail remains unknown.

Requires curl, gh, shasum and tar on Linux or macOS (amd64 or arm64). The installer downloads and verifies fleetdiff v0.7.0; analysis reads your local file. For a manual installation, see release verification.

curl -fsSLo install-fleetdiff.sh https://raw.githubusercontent.com/llm-measurement/fleetdiff/v0.7.0/scripts/install.sh
sh install-fleetdiff.sh v0.7.0 ./bin
./bin/fleetdiff investigate --litellm-spend ./spend.csv --group-by session

The default compares two complete seven-day periods. Choose --group-by key for keys, or explicit period flags for shorter files.

Reading the result

How much input was reused?

Both periods record 2,000 input tokens and 200 output tokens. Every request reports cache-read and cache-write detail, so the denominators cover all input in this example:

Uncached input is input minus cache reads; it includes cache writes. Cache reads and writes are subsets of recorded input. Shares measure input tokens.

Which key's uncached input grew?

The keyed uncached-growth ranking uses requests with usable cache-read detail and a group identity. In this fixture, key-1 rises from 80 to 700 uncached input tokens while the other key stays flat. The report's local aliases refer to the same identities in its total-token and cache rankings.

For another view, choose --group-by team, user, end-user or session. Rankings carry bounds when the sketches cannot identify an exact change.

Check coverage before interpreting a change

Each cache field has its own covered-input denominator and request count. Missing, invalid and subset-violating details are excluded and counted separately; requests without group identities stay outside the ranking. Explicit zero detail is recorded zero, not proof of provider origin. A missing detail or zero denominator leaves the share unavailable.

For your own data, use the released request-level export path. The SQL includes cache fields by default, but the pinned writer and export mappings determine which details survive. Keep raw exports private. The LiteLLM spend guide checks total usage and log completeness; the trace check checks usage and identity fields in an OTLP capture.

What to check next

If the recorded share falls, review the provider's cache diagnostics and whether the gateway route preserves cache markers.
